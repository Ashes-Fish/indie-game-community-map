# 全国版优化方案

> 状态：O1 已完成（2026-11-13，第 7 节），O2 已完成（2026-11-14，第 8 节），O3 已完成（2026-11-14，第 9 节；建筑压缩纹理见第 10 节），O4–O5 未实现。对象是 `national` 分支（工作目录 `游戏社群网站-线上版`），基线版本 `8d61979`。
> 接在《全国一张世界方案》M2 之后，覆盖原 M3（手机专项）和 M4（打磨）里的性能部分，并补上实测发现的问题。

## 1. 现状实测

**测量方法**：`vite build` 生产包，本地静态服务器，Chrome 窗口 1280×720、像素比 1.5（桌面档，含后期），显卡是本机 AMD 集成显卡（ANGLE / D3D11）。不是真机手机数据。

### 1.1 体积

| 项目 | 大小 | 说明 |
|---|---|---|
| 代码 | 1.2 MB（压缩后约 0.4 MB） | 主包 879 KB，后期 242 KB |
| 地块数据 7 块 | 1.5 MB | 长三角 521 KB，其余 93–245 KB |
| 全国纸面数据 | 0.9 MB | `elev.png` 530 KB + `map.json` 395 KB |
| 建筑模型 | 3.9 MB | 实际用到的 `m_*` 2.8 MB；`a_`/`b_` 共 1.0 MB 只给 `?asset=a|b` 对比用 |
| 地形贴图 | 0.5 MB | |
| **合计** | **7.9 MB** | |

### 1.2 加载

- 打开到可操作：**约 8.2 秒**（本机，本地服务器，无网络延迟）。
- 每个地块的 `height.png`、`water.png`、`rivers.json` 被请求 **4 次**，全国纸面的 `map.json`、`relief.json`、`elev.png` 各 **3 次**：页面主线程取一次，纸面绘制的 3 个后台线程（Worker）又各自取一遍、各自解码。
  - **更正（O1 实测）**：同一个页面里浏览器缓存会接住这些重复请求，服务器端每个文件只被下载 1 次，所以**没有多花网络流量**（初稿写的"约 5.7 MB 重复下载"不对）。重复的代价是每个线程各自解码一遍 PNG 和 JSON，以及在没有缓存头的服务器上真的会多下载。
- 加载期间还会把**西安**地块完整建好（城市、据点、树木、编译着色器）：首屏默认视角是全国，`patchAt` 按"离边缘最远"挑地块时选中了西安。
  - **更正（O1 实测）**：慢的主要不是建西安，而是建好后第一次画它时，地形着色器（约 12 万字符）在显卡驱动里链接，主线程要**等 2.6–3.6 秒**。

### 1.3 帧时间（主线程每帧间隔）

| 视角 | 中位数 | 95 分位 | 最差 |
|---|---|---|---|
| 片区（1500 km） | 11.1 ms | 14.9 ms | 174 ms |
| 长三角全景 | 11.2 ms | 42.6 ms | 89 ms |

- 全国视角和杭州近景这两项没测出有效数据：测量窗口被浏览器节流成每秒 1 帧，数字作废。M2 结果里的 GPU 数据（全国 5.6 ms、长三角全景 13.8 ms / 308 次绘制、杭州 7.5 ms）仍可参考。
- **长三角全景 95 分位 42.6 ms**：镜头停住后，附近地块还在陆续建中层、近层，这些建造挤占主线程，造成掉帧。
- **静止时一直在画**：镜头完全不动，每秒仍然画满 60 帧（水、炊烟、鸟、旗子在动）。手机上这是发热、耗电的主要来源。

### 1.4 代码里看到的其他问题

- 地形网格、六边形、法线图、AO 细分都在浏览器主线程现算（`gridGeometry`、`buildHexes`、`buildNormalTex`、`bakeAO` 的细分部分）。
- 设备分档只有"手机/桌面"两档，按屏幕和触屏判断；帧率低时只会降分辨率，不会关阴影、减树木。
- 贴图都是 PNG/WebP，进显卡后不压缩。
- 城市颜色槽位上限 32（`MAX_OWNERS`），社团城市超过 31 座时领土颜色会出错。
- GitHub Pages 缓存只有 10 分钟（`Cache-Control: max-age=600`），国内访问慢且不稳定。

## 3. 优化项（按收益排序）

### P0：加载（收益最大、改动最小）

1. **数据只下载一次。** 页面主线程下载并解码地块和全国数据后，用 `postMessage` 的可转移对象（ArrayBuffer）一次性发给纸面 Worker；Worker 不再自己 `fetch`。下载量直接减少约 5.7 MB，解码时间也省掉 3 份。
2. **首屏不再预建西安。** 全国视角下 `warmUp` 只做着色器预编译，不建任何地块的城市和树木；等镜头真的往某个地块靠近时再建。修正 `startView` 默认视角下 `patchAt` 选中西安的问题。预计首屏少 2.5–3 秒。
3. **首屏只下载必要的。** 全国视角只需要：代码、全国纸面数据、城市索引、各地块的低精度地形。地块的 `water.png`、`rivers.json` 和全部建筑模型推迟到镜头靠近时再下载。
4. **删掉对比用模型。** `a_*`、`b_*` 模型（1.0 MB）只给 `?asset=` 对比用，移出 `public/`，放到 `assets-src/`。
5. **后期效果（`post.js`，242 KB）推迟加载。** 全国视角用不到后期，进入片区视角时再加载。

### P1：帧率与发热

6. **不动就少画。** 镜头静止 2 秒后，手机降到每秒 15 帧、桌面 30 帧（只保留水和旗子这类轻量动画）；任何操作立即恢复 60 帧。页面切到后台时完全停画（`visibilitychange`）。手机发热主要靠这一项解决。
7. **建造分帧、限时。** 地块中层、近层的建造现在一次占主线程几十到几千毫秒。改成每帧最多占 4 ms 的任务队列：镜头在动时只建当前视野需要的，停下后再建周边。
8. **材质合并与实例化。** 长三角全景 308 次绘制主要来自城市、据点、道路、河流各自一份网格和材质。
   - 同一个建筑模型出现多次时用 `InstancedMesh`（一次绘制画全部）。
   - 每个地块的道路、河流各合并成一个网格。
   - 低多边形建筑共用一张颜色贴图（调色板），合并成少数几种材质。
   - 目标：长三角全景 100 次绘制以内。
9. **阴影按距离分级。** 片区视角（超过 300 km）关掉实时阴影，只用烘焙进地形的明暗；近景才开实时阴影，阴影贴图按机器分档 1024/2048。

### P2：手机专项（原 M3）

10. **设备分三档。** 首次打开读 `navigator.deviceMemory`、显卡名称（`WEBGL_debug_renderer_info`）、CPU 核数，再测头 60 帧，分成低 / 中 / 高三档并记到 `localStorage`。每档控制：渲染分辨率、阴影、后期、树木密度、同时驻留的地形块数、纸面 Worker 数。帧率持续偏低时整档下调，不只是降分辨率。
11. **压缩纹理。** 地形贴图、建筑贴图改用 KTX2（Basis Universal），进显卡后仍是压缩格式，显存占用降到 1/4–1/6，上传也更快。需要在烘焙流程里加一步转换。
12. **地形网格不在浏览器里算。** 所有地形块共用一张平面网格，在顶点着色器里按高程图抬高（显卡做），主线程不再逐块构建几何体。六边形数据、法线图改为烘焙时生成文件。
13. **低档兜底。** 不支持 WebGL2 或分到"低"档且帧率仍不足时：只显示全国纸面 + 城市旗标 + 社团列表，3D 地块不建。

### P3：网络与发布

14. **国内可访问的托管。** GitHub Pages 在国内慢且偶尔打不开，比体积影响更大。可选：
    - jsDelivr 镜像仓库（零成本，可直接用 GitHub 仓库地址）；
    - 国内对象存储 + CDN（需要备案）。
15. **长缓存。** 带哈希的文件（`assets/*-<hash>.js`、模型、地块数据加版本号）设一年缓存；`index.html` 不缓存。
16. **预连接。** `index.html` 加 `preconnect` 到资源域名。

### P4：可扩展性（社团城市增多以后）

17. **城市颜色上限从 32 提到 255。** 领土颜色改用一张 256×1 的颜色贴图，不再用 uniform 数组。
18. **地块按需下载。** 现在 7 个地块全部在首屏下载；社团城市多到几十个后，改为只下载视野内和附近的地块，离开的释放显存（最近最少使用缓存）。
19. **社团列表虚拟滚动。** 社团数到几百个时，列表只渲染可见的那一屏。

## 4. 分阶段

| 阶段 | 内容 | 预计效果 |
|---|---|---|
| **O1 加载** | P0 全部（1–5） | 首屏下载约 8.7 MB → 1.5 MB，可操作时间 8.2 s → 约 3 s |
| **O2 帧率** | 6–9 | 静止不发热；长三角全景 95 分位降到 20 ms 内，绘制 100 次内 |
| **O3 手机** | 10–13 | 中端手机达标；低端机有兜底 |
| **O4 发布** | 14–16 | 国内打开稳定；二次打开秒开 |
| **O5 扩展** | 17–19 | 支持上百座社团城市 |

建议先做 **O1**：改动集中在 `scene.js`、`natink.js`、`paperWorker.js`、`natdraw.js` 四个文件，风险低、收益最大，做完马上能感觉到。

## 5. 每阶段怎么验收

- 用同一套脚本测：生产包、固定窗口 1280×720、四个视角（全国 / 1500 km / 长三角全景 / 杭州近景）各取 180 帧的中位数、95 分位、最差值，加上首屏时间、请求数、下载量、绘制次数。测量窗口必须关掉浏览器后台节流，否则数据作废（本次全国和杭州两项就是这样作废的）。
- 手机至少用一台中端安卓真机（约 2021 年后的千元机）测 O2、O3。

## 6. 需要确认

1. 先做 O1 是否可以。
2. 托管：用 jsDelivr 镜像，还是国内对象存储 + CDN（后者需要备案）。
3. 压缩纹理（第 11 项）要改烘焙流程，是否接受多一步转换工具（`toktx` 或 `gltf-transform`）。

## 7. O1 结果（2026-11-13）

### 做了什么

| 项 | 做法 | 文件 |
|---|---|---|
| 数据只取一次 | 页面主线程一次取回全国和各地块数据（`fetchNationalData`），原始字节复制给纸面 Worker、交给 3D 地块解码；Worker 不再自己请求 | `natdraw.js`、`natink.js`、`paperWorker.js`、`world.js`、`scene.js` |
| 地形着色器提前编译 | 一开始加载数据时就把地形着色器交给显卡驱动编译（`precompileTerrain`），和下载、解码同时进行 | `scene.js` |
| 首屏不再预建地块 | 全国视角直接显示，不在加载页后面建地块。长三角改为地图出来后在后台建好、编译所需着色器，第一次放大时不用再等；后台这一步会让画面顿几下，所以只在地图静止时做（加载页消失 2.5 秒后、用户 1.2 秒没有拖动或缩放、镜头没在飞）。分享链接（`?view=`、`?open=`、`?region=`）仍在加载页后面先建好所在地块 | `scene.js` |
| 对比用模型不进发布包 | `a_*`、`b_*` 模型留在 `public/models`（开发时 `?asset=a|b` 仍可用），打包时从输出里删掉 | `vite.config.js` |

**没做的**：
- 第 3 项"首屏只下载必要的"：全国纸面在地块范围内要用该地块的精细高程和水系来画海岸、湖泊（`natdraw.js loadFine`），所以各地块的 `height.png`、`water.png`、`rivers.json` 首屏就要；要推迟它们，得先把纸面改成"地块数据到了再重画那几张瓦片"，留到 O5 第 18 项（地块按需下载）一起做。
- 第 5 项 后期效果（`post.js`）推迟加载。实测它压缩后 236 KB、和其他文件并行下载，加载页本身不等它，推迟收益很小，而全国视角也在用后期画面；留到 O3 设备分档时再按档决定。
- 第 4 项的做法和初稿不同：模型没有移出 `public/`，只是不进发布包，开发时的对比功能保留。

### 实测（生产包，本地静态服务器带 10 分钟缓存头，同 GitHub Pages；Chrome 无界面模式，真显卡，1280×720；新旧交替各测 3 次取中位数）

| 指标 | 改前 | 改后 |
|---|---|---|
| 打开到可操作，无限速 | 8.66 s | **4.60 s** |
| 打开到可操作，模拟 4G（9 Mbit/s，60 ms） | 10.66 s | **6.45 s** |
| 发布包体积 | 7.9 MB | 6.9 MB |
| 可操作后 3 秒内累计下载量 | 3.6 MB | 6.0 MB（见下） |
| 飞到杭州近景最长一帧（加载后 8 秒开始飞） | 630 ms（无限速）/ 401 ms（4G） | 426 ms / 326 ms |
| 飞行中超过 100 ms 的帧数 | 17 / 17 | 14 / 7 |
| 画面 | — | 全国视角逐像素一致；长三角、杭州、成都差异 < 0.2% 像素（树木、鸟群动画时刻不同） |

- **下载量反而多了**：以前地图出来之前只下载了西安用到的 3 个建筑模型；现在后台预建长三角，地图出来后几秒内会下载长三角的 10 个建筑模型（约 2.4 MB）。总量不变（以前放大到长三角时也要下），只是提前了。手机流量敏感的话，O3 可以改成"Wi-Fi 下才预建"。
- **全国视角帧率**：本机集成显卡上全国视角本身只有 25–45 帧，新旧版都是，每次测量波动很大，O1 没有改变它。这是 O2 的范围。
- **后台预建会让地图顿几下**：加载后约 3–6 秒内，地图静止时有几次 0.2–0.9 秒的停顿（着色器链接、2048 像素的建筑贴图上传）。以前这些发生在加载页后面；现在挪到了地图出来之后，并且只在没有操作时发生。O2 第 7 项和 O3 第 11 项（压缩纹理）会继续压低。
- **飞到杭州时仍有 300–500 ms 的卡顿**：来自飞行途中现建的近处地形块和其他地块的中层，O1 没有处理，是 O2 第 7 项（建造分帧限时）的目标。

## 8. O2 结果（2026-11-14）

### 先测清楚瓶颈在哪

方案初稿把"长三角全景 308 次绘制"当作 O2 的主攻点。逐帧拆开测（按场景部分统计每帧绘制次数，再逐项关掉某部分看整帧显卡耗时）后，结论不同：

- **绘制次数不是瓶颈。** 单帧实际是：长三角全景主画面 168 次 + 阴影 107 次，杭州近景 89 + 37 次（M2 的 308 是把多帧累加了）。这台集成显卡上，把建筑、道路、河流等物体全部隐藏，整帧只省 1–2 ms；合并、实例化收益很小，本轮不做。
- **真正的大头是全屏像素**：地形与古舆图纸面的着色器、后期效果（景深模糊、辉光、抗锯齿），以及一直不停地画——静止时也每秒画满。
- **飞行卡顿**的直接原因是：飞行途中第一次画近处地形的阴影时，驱动才把阴影着色器真正编译完（250–450 ms 一次）。

### 做了什么

| 项 | 做法 | 文件 |
|---|---|---|
| 静止降帧 | 镜头、建造、展开动画、点选高亮都停下 2 秒后，桌面每秒画 30 帧、手机 15 帧；任何输入立刻恢复。动画按真实时间推进，只是没那么顺，不会变慢。地址加 `?idle=0` 可关掉 | `scene.js`（`loop`、`busyReason`） |
| 阴影按需重画 | 阴影贴图改为手动更新：动的时候每帧画，静止时隔帧画，全国视角不画 | `scene.js` |
| 景深模糊提前退出 | 移轴景深在清晰带里（全国视角几乎整屏）直接取原像素，不再做 13 次采样 | `post.js` |
| 屏幕空间 AO 不再为透明物体多画两遍 | N8AO 的"透明感知"模式会把整个场景多画两遍、多遍历三次；场景里的透明物体（河、路、炊烟、旗光）贴地或悬空，关掉看不出差别 | `post.js` |
| 地形阴影着色器提前编译 | 加载时就编译地形的阴影着色器；后台预建长三角时，太阳和阴影相机也对准那里画一帧，让驱动真正编完 | `scene.js` |
| 静态物体不再每帧重算矩阵 | 地块建好后，不会动的物体关掉 `matrixAutoUpdate`（据点生长、旗、黄山、商队、船、行人、鸟仍照常） | `scene.js`（`freezeStatic`） |

**没做的**：建造分帧限时（原第 7 项）——新老版本对比显示建造本身已不是卡顿主因（见下），留到 O3 看手机上是否需要；材质合并与实例化（原第 8 项）——实测收益小，见上。

### 实测（生产包，Chrome 无界面模式，真显卡，1280×720；与 O1 版本交替测，取中位数）

| 指标 | O1 | O2 |
|---|---|---|
| 地图静止时，每秒实际画的帧数（全国 / 长三角 / 杭州） | 84 / 43 / 39 | **30 / 28 / 29** |
| 全国视角每帧耗时（逐项开关测法） | 10.7 ms | **6.7 ms** |
| 飞往杭州：超过 60 ms 的帧（中途改动前的测量） | 23 帧，合计 2.3 秒 | 7 帧，合计 1.1 秒 |
| 飞往成都：同上 | 20 帧，合计 2.6 秒 | 8 帧，合计 1.2 秒 |
| 飞行途中驱动现编译着色器造成的停顿 | 杭州 1 次 230 ms，成都 1 次 320 ms | **0 次** |
| 画面 | — | 全国、长三角、杭州、成都四个视角差异 ≤ 0.12% 像素（动画时刻不同） |

- **静止省电**：O1 在这台机器上静止时每秒画 39–84 帧（画多少取决于显卡跟不跟得上），O2 稳定在 28–30 帧，显卡工作量降到原来的三分之一到四分之三。手机上降到每秒 15 帧，省得更多，但没有真机数据。
- **飞行流畅度的最后一次对比**（两版都加载后等 14 秒再飞）差别变小：杭州 8 vs 9 帧、成都 8 vs 10 帧超过 60 ms。原因是 O1 那一版后台预建长三角时，也恰好把阴影着色器编完了；O2 的阴影提前编译主要帮助的是"一打开就飞"和"飞往从没去过的地块"的情况。剩下的 250–400 ms 停顿来自飞行中现建细地形块和其他地块的中层，要靠 O3 的"地形网格交给显卡算"解决。
- **显卡耗时测量这台机器上很不稳定**：同样的设置，单次测量从 13 ms 到 28 ms 都出现过；所以上表只采用新旧交替、多次取中位数的结果，单项小于 1–2 ms 的差别不作结论。

### 还没解决

- 长三角全景、杭州近景**在动的时候**每帧显卡耗时仍约 20 ms（这台集成显卡上约 45 帧），主要是地形与纸面着色器的全屏计算。这是 O3 的重点：按设备分档降分辨率、手机关后期，再看着色器能否把远处的细节分支跳过。
- 真手机没测。

## 9. O3 结果（2026-11-14）

### 做了什么

1. **设备分三档**（新文件 `tiers.js`）。第一次打开按内存、CPU 核数、显卡名称猜档：软件渲染或内存 ≤ 2 GB → 低；手机（触屏且短边 < 900 px）最高到中档，弱显卡（Mali-G7x 及更早、Adreno 5xx 及更早、PowerVR）→ 低；桌面弱显卡（老款 Intel 核显）或内存 ≤ 4 GB → 中；其余 → 高。结果记在 `localStorage`（换了屏幕类型会重猜），`?q=low|mid|high` 可强制。每档控制：

   | | 低 | 中 | 高 |
   |---|---|---|---|
   | 渲染分辨率（倍数） | 1 → 可降到 0.6 | 1.5 → 可降到 0.75 | 1.5 → 可降到 1 |
   | 后期（景深、泛光、近景 AO） | 关 | 关 | 开 |
   | 阴影贴图 | 关 | 1024 | 2048 |
   | 地形着色器 | 简化 | 简化 | 完整 |
   | 树木 / 炊烟行人鸟群 | 35% / 50% | 60% / 75% | 100% |
   | 纸面贴图缓存（块） | 24 | 40 | 80 |
   | 静止时每秒帧数 | 12 | 20 | 30 |

   高档和 O2 完全一样：全国、长三角、杭州、成都四个视角截图对比，差异 ≤ 0.03% 像素。

2. **运行中自动降档**：先降分辨率（低档、中档允许降到 1 倍以下——地形着色器按像素付费，长三角全景少一半像素就少一半多耗时，HTML 文字和面板不受影响）；分辨率到底后，手机持续 6 秒低于 30 帧、桌面低于 20 帧才整档下调，并记住。建造、地块升起、纸面绘制期间的帧不计入整档判断——第一版就因为加载后几秒的后台预建，把这台桌面错降成了中档。`?q=` 强制时不自动降档。

3. **低档兜底**（新文件 `lite.js`）：浏览器不支持 WebGL2，或 `?lite=1`，直接显示平面古舆图（和 3D 版纸面同一个绘制器），每个有社团的城市一枚印章（数字 = 社团数）、社团列表和详情面板照常可用；拖动、滚轮、双指缩放，点印章打开社团。3D 部分（three.js 等）不下载。实测禁用 WebGL 的 Chrome 0.5 秒可用，无报错。

4. **飞行中的着色器卡顿**（中、低档）：没有后期时，预热帧画到了离屏目标，而正式画面直接画到屏幕（色调映射是着色器的一部分），所以飞行时又编译了一遍，停顿 430–530 ms。改为预热也画到屏幕（1×1 像素）后，飞行途中编译次数为 0。

### 实测（生产包，Chrome 无界面模式，真显卡，桌面 1280×720 / 手机 390×844 三倍屏；各档用 `?q=` 强制）

每帧显卡耗时（ms，全国 / 长三角全景 / 杭州近景，静止时取中位数）：

| | 高 | 中 | 低 |
|---|---|---|---|
| 桌面 1.5 倍屏 | 21 / 37 / 36 | 5 / 28 / 22 | 9 / 19 / 14 |
| 手机尺寸 3 倍屏 | 11 / 22 / 15 | 2 / 14 / 4 | 2 / 12 / 5 |

持续拖动地图时的实际帧率（桌面 1280×720，加载后等 25 秒，自动降分辨率生效后）：

| | 长三角 | 杭州 |
|---|---|---|
| O2（即高档） | 14 | 14 |
| O3 中档 | 21 | 25 |
| O3 低档 | 30 | 37 |

飞往城市（加载后 14 秒，桌面 1.5 倍屏，8 秒飞行内超过 60 ms 的帧）：低档杭州 / 成都 14 / 11 帧，各有 1 次 300 ms 以上的停顿。高档在这台机器上飞行时本身只有约 15 帧，几乎每帧都超过 60 ms（78 / 60 帧），这个指标对它没有意义；高档代码与 O2 相同。

### 结论与没做的

- **"地形网格交给显卡算"（原第 12 项）不做了**：逐块计时，飞行中一块细地形的构建只要 1–18 ms，不是停顿来源；剩下 1 次约 300 ms 的停顿在飞行开始后 0.3–0.4 秒，来自其他地块中层的首次绘制，O4/O5 再看。
- **长三角全景的瓶颈是地形着色器的光照部分**：在低档上把地形整个隐藏，每帧 28 ms → 6 ms；只把光照换成平涂，28 → 17 ms；而贴图层、水面、农田、边界各自关掉都不到 1 ms。所以按档降分辨率是最直接的办法；进一步要把地形光照从 `MeshStandardMaterial` 换成简化光照，会改变画面，需要先看效果再定。
- **压缩纹理（原第 11 项）**：随后单独做了建筑部分，见第 10 节。
- **这台集成显卡上高档拖动长三角只有约 14 帧**，桌面低于 20 帧时会自动降到中档，所以实际用户看到的是中档效果。若希望它保持高档画面，可以把高档改成"长三角全景时关后期"。
- 真手机仍没测；"手机最高中档"是按经验定的，拿到真机数据后再调。

## 10. 建筑贴图改 KTX2（2026-11-14）

### 做了什么

- 13 个现代建筑模型（`public/models/m_*.glb`）的贴图从 WebP 改成 KTX2（Basis ETC1S，最高质量档）。转换加进 `assets-src/build_modern.sh`：从 Blender 烘焙原件（PNG 贴图）出发，几何照旧 meshopt 压缩，贴图用 `gltf-transform etc1s`（底层是 KTX-Software 4.4 的 `toktx`）。新增 `SKIP_BAKE=1` 只重压不重烘焙。机器上要装 KTX-Software（Windows `scoop install ktx-software`）。
- `assets.js` 给 GLTFLoader 配上 `KTX2Loader`：浏览器按显卡支持的格式转码（桌面 BC7、手机 ASTC/ETC2），转码器（wasm，约 250 KB 压缩后）只在第一个建筑加载时下载，平面兜底模式不下载。
- 地形贴图（`tex/terrain.webp`）没改：只有 512×512×6 层、显存约 8 MB，透明通道存的是高度，ETC1S 压它容易失真，收益不值得。

### 实测（生产包，Chrome 无界面模式，真显卡，1280×720 1.5 倍屏，直接打开杭州近景；新旧各 3 次取中位数）

| 指标 | WebP | KTX2 |
|---|---|---|
| 建筑贴图显存（11 张，含 mipmap） | 123 MB | **31 MB** |
| 贴图上传总耗时（主线程） | 510 ms | **45 ms** |
| 单次最长上传 | 260–320 ms | **15–30 ms** |
| 下载：用到的建筑模型 | 2.1 MB | 3.9 MB |
| 下载：转码器 | 0 | 0.57 MB（未压缩；gzip 后约 0.25 MB） |
| 画面（杭州 70 km / 22 km、上海 22 km 截图） | — | 差异 ≤ 0.23% 像素 |

- **显存降到四分之一、上传卡顿基本消失**：一张 2048 的城市中心贴图以前上传 + 生成 mipmap 要 100–300 ms（一帧明显卡住），现在 15–30 ms。对手机最有意义——显存小的机器以前最容易因为贴图爆显存而崩页。
- **代价是下载变大**：ETC1S 在磁盘上比 WebP 大约 1.8 倍，加上转码器，杭州近景多下载约 2.3 MB。13 个模型全部合计 2.9 MB → 5.2 MB，但每个城市只下载自己用到的几个。画质更高的 UASTC 格式会再大 3 倍，没选。
- 首屏时间不变（建筑在地图出来之后才加载）。

### 测量中碰到的问题

- 测量中偶尔出现地形上整片三角形明暗块（像网格的每个三角面单独着色）。它在 WebP 版和 KTX2 版上都出现过、O2/O3 提交版本的重复测试里没出现，一出现就一直存在直到刷新，重新上传地形贴图、重建 mipmap、关阴影、换分辨率都不能让它消失；之后又连续测了 KTX2、O3、O2 各 8 次加 WebP、KTX2 各 12 次，都没再出现。WebP 版也出过，所以看不出和 KTX2 有关；当时这台机器同时开着十几个测试浏览器，可能与显卡驱动在高负载下出错有关，原因没查清，记为待查。真机上若有人看到同样的三角块，再回来查。

## 11. 首次打开不卡、地形贴图加细（2026-11-18）

用户反馈：第一次打开网站还是比较卡。要求：加载可以久一点，进入画面后不卡；地形材质再细一些。

### 卡在哪

以前全国视图一出来就撤掉加载画面，2.5 秒后在后台建长三角（编译着色器、上传顶点和贴图），第一次飞进某个城市时再建沿途的大区、画纸张瓦片、建更细的地形块。用户正在看的画面因此一卡一卡。实测（桌面 GPU，生产构建，冷缓存）：

| | 改前 | 改后 |
|---|---|---|
| 加载画面撤掉 | 2.9 秒 | 13–15 秒（手机模拟 4× 降速：19 秒） |
| 进入画面后 25 秒内超过 50 ms 的帧 | 13 帧，最长 401 ms，共 1.8 秒 | 0–3 帧，最长 78 ms |
| 第一次飞到杭州 | 17 帧，共 1.8 秒，最长 250 ms | 4–10 帧，最长约 110 ms |
| 第二次飞到杭州 | 4 帧 | 0 帧 |

### 改了什么（`src/scene.js`）

1. **全部放在加载画面后面做**：长三角的城市、近景、着色器（以前在后台），再加其余各大区的城市层（以前第一次飞过去时才建），离起始视图近的先建。低档设备（low）仍然只建长三角，加载短一些。
2. **`settle()` 预演**：加载画面撤掉前，真实渲染几十帧——每个大区俯视两帧（上传建筑顶点、建地形块），再按真实速度飞一趟"全国 → 杭州 → 全国"（沿途纸张瓦片画好、细地形块建好），最后停在起始视图，直到连续几帧都便宜、纸张瓦片都画完。动画时钟和"大地从纸上升起"的进度都会还原，所以撤掉加载画面后入场动画照常。手机最多 12 秒、桌面最多 8 秒，超时就不等了。
3. 进度条在这一段也会走（88% → 99%），文字是"正在营建城郭…""即将完成…"。

### 地形贴图（`scripts/paint_textures.py`、`src/terrain.js`）

- 六层手绘贴图从每层 512² 改成 **1024²**（在 2048² 画布上画，笔触数量和尺寸按分辨率放大，密度不变、单笔更细）。
- 首屏仍用 512² 版（`tex/terrain.webp`，557 KB，由同一张图缩小，画面一致）；地图出来 1.5 秒后后台下载 **`tex/terrain-hd.webp`**（1.4 MB），在 Worker 里解码成像素，每帧上传一层，六层都到 GPU 后再换上。一次性整体上传会卡一帧 160 ms，这样拆开以后没有卡顿。低档设备不下载高清版。
- 着色器近景多一个旋转、缩小的细节层（只在很近、桌面档时），街景下草地、林地、岩石看得出笔触，不再是一片糊的绿。
- 重画贴图后各层平均色略变，着色器里的 `M_GRASS` 等平均色同步更新，整体色调不变。

## 12. 去掉摆动、地形网格加细（2026-11-18）

- **树和草不再摆动**：树（`props.js` 的 `fogPatch` sway）和水田随风起伏（`terrain.js` 的 wave）都删了；旗子还在飘。
- **地形网格加细**：近景地形块的格距从 1 km 改成 0.5 km（触屏版 1.5 → 1 km），每块 128 km 的顶点从 1.7 万增到 6.7 万。只是格子变密没用（高程数据本身是 0.75 km 一格），所以近景网格另加一层小起伏 `World.meshY`：平原上缓缓的小土包，山地上随坡度加强的褶皱；城市、据点平整过的地面、水面和岸边都不加（`flatten()` 同时记一张 `flat` 遮罩）。树、房子、道路、河流、行人跟着 `meshY` 落地，不悬空；建筑和城市仍按原高程。
- 着色器里把网格法线和烘焙法线的差叠到地面法线上（160 km 以内），这层起伏在光照下看得出来。
- 性能：杭州近景平移约 13 ms 一帧；首次飞到杭州 5 帧超过 50 ms（最长 127 ms），第二次 0 帧。

## 13. 地表贴图改卡通风；修复高档画质大区视图全白（2026-11-18）

- **贴图重画**（`scripts/paint_textures.py`）：用户觉得原贴图（照片感的细碎草叶、裂纹石头）难看，要更接近《文明6》式的卡通风。六层全部重画成平涂风格：3–4 个色阶的大色块、柔和但清楚的边，草地上稀疏的三叶草簇和成簇小花，林地是带亮面 / 暗面 / 高光和深色描边的圆润灌木团，岩石是平涂多边形石块加上沿亮边、下沿暗边，沙地是宽柔沙纹，雪是白与浅蓝两色雪堆，水田是平涂秧苗行加亮青水面。贴图也小了：首屏 261 KB（原 557 KB），高清 631 KB（原 1.4 MB）。
- 着色器（`src/terrain.js`）：草地颜色改为以贴图本身的色块为主（原来只取明暗、压掉色相）；各区域底色调亮、提高饱和（`C_GRASS` 等）；大尺度噪声压暗从 ±15% 降到 ±7%；去掉上一版加的近景细节层（会把平涂色块弄糊）；宏观混合从 0.32 降到 0.18。
- **修复**：上一版（c639a97）近景网格法线叠加在少数像素上算出零向量，normalize 得到 NaN；高档画质的泛光（bloom）把 NaN 模糊到整个屏幕，结果在长三角等大区视图下陆地整片不显示、只剩纸面。现在法线为零或朝下时退回烘焙法线，NaN 像素为 0。中低档没有泛光，不受影响。
