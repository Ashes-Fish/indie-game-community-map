# v2-civ 城市规模与据点方案

> 状态：第 1–4 节已在 `v2-civ/` 实现；第 5 节（上传后端）待定。阈值与聚落格采用推荐值。

### 新增社群后的维护流程

1. 在 `site/data/communities.json` **末尾**追加社群（落位按顺序进行，追加不会挤动旧社群）。城市不在 `data.js` 的 `CITIES` 里时需先加城市。
2. 本地 `npm run dev` 打开，在浏览器控制台运行 `__dbg.pins()`，把输出覆盖到 `v2-civ/src/layout-pins.json` 并提交。这样新落位被固定下来，城市半径也被记住（用于缩小时的缓冲）。
3. 推送到 `main` 后 GitHub Actions 自动部署。

### 调试参数

- `?mock=shanghai:40,hangzhou:12`：给城市加占位社群，测试分档和聚落格。
- `?custommodels=1`：本地打开自定义模型加载（线上默认关闭）。

网站会长期维护，并开放用户自主上传据点。国内社群分布很不均匀，少数城市有数个乃至数十个社群，因此城市范围要按社群数量自动决定，而不是手写。

## 现状与问题

| 现在的写法 | 问题 |
|---|---|
| 城市范围手写：`src/data.js` 的 `CITIES[].radius` | 用户上传后没人维护这个数 |
| 社群只放在城市中心第一圈 6 格（`src/world.js` 的 `buildHexes`） | 一座城最多 6 个社群 |
| 造型、logo、朝向手写：`data.js` 的 `META` | 用户上传的社群没有这些信息 |
| 领土重叠时"离谁近归谁" | 大城扩张会吞掉邻近小城 |

## 1. 城市范围：按社群数量分档

半径 R 格时，中心之外可用 3R(R+1) 格：R1=6、R2=18、R3=36、R4=60、R5=90、R6=126。按社群约占可用格一半分档：

| 档位 | 半径 | 社群数 | 城池外观 |
|---|---|---|---|
| 小镇 | 1 | 1，且为县级市或被邻城挤压 | 小城郭 |
| 默认 | 2 | 1–8 | 现有样式 |
| 府城 | 3 | 9–18 | 加一圈城墙、多一个地标 |
| 大都会 | 4 | 19–30 | 双重城郭 |
| 都城 | 5 | 31–45 | 更大 |
| 超大 | 6（上限） | 46+ | 配合聚落格 |

- 用固定阈值，不按全国排名分档，避免一座城的变化牵动别的城。阈值定期按真实分布复核。
- 缓冲：超过阈值立即扩大；低于阈值 2 个才缩小。
- 每座城可设 `radiusOverride` 手动覆盖。

## 2. 社群落位

- 从城市中心一圈圈向外找空格；打分沿用现有逻辑（靠近真实地址方向、避开水面和陡坡）。
- 落位结果持久化保存。新社群只填空位，旧社群不移动。
- 聚落格：社群数超过可用格约 60% 时，多个小社群可共用一格（多面旗），点开列出全部。

## 3. 相邻城市的领土

- 各城中心同时向外扩张；每座城保底第一圈；冲突格按"距离近、规模大"判定。
- 社群只落在本城领土内；被挤压的城市优先向空地多扩一圈，不侵占邻城。

## 4. 据点造型与自定义模型接口

### 数据字段

社群记录用 `model` 字段描述外观，取代现在的 `style`：

```js
// 内置造型（现有 7 种：guild、tulou、cyber、observatory、paifang、savepoint、pinewood）
model: { kind: 'builtin', style: 'tulou' }

// 自定义模型（预留，暂不开放）
model: {
  kind: 'custom',
  url: 'models/<社群key>.glb',   // 审核通过后存放的位置
  sha256: '…',                     // 审核时记录，加载时校验
  fallback: 'tulou',               // 加载失败或未审核时显示的内置造型
}
```

缺省（没有 `model`）时按社群名哈希分配一种内置造型。

### 渲染接口

`src/places.js` 的 `buildDistricts` 不再直接调用 `STYLES[cm.style]`，而是经过一个造型注册表：

```js
// 每种 kind 提供一个构建函数，返回放在本格中心、底部贴地的 THREE.Group
registerModelKind('builtin', (cm, ctx) => buildBuiltin(cm.model.style, ctx));
registerModelKind('custom',  (cm, ctx) => loadCustom(cm.model, ctx));   // 先返回 fallback，加载完成后替换
```

- 旗帜、logo、悬停高亮、点击飞入由系统统一添加，与造型无关。
- 自定义模型的加载是异步的：先显示 `fallback` 内置造型，加载并校验成功后再替换，失败则保留 fallback。

### 自定义模型的约束（开放时生效）

- 格式：glTF 2.0 二进制（`.glb`），不执行脚本、不支持外链资源。
- 体积：文件 ≤ 2 MB，三角面 ≤ 2 万，贴图 ≤ 1024×1024。
- 尺寸：自动缩放到一格以内（包围盒半径约 3.5 单位），底部对齐地面。
- 画风：默认把材质换成站内统一的低多边形材质，让上传模型与整体美术一致；可选"保留原贴图"，需审核通过。
- 必须人工审核后才上线。

### UI 预留

- **社群侧面板底部**：加一个"自定义据点模型"按钮，置灰不可点，显示"敬请期待"。
- **以后的上传表单**：在"据点外观"一栏列出 7 种内置造型可选，最后一项是"上传自定义模型"，同样置灰并显示"敬请期待"。

## 5. 数据与上传

- 社群记录：统一城市编号（行政区划代码）、可选经纬度、`model`、审核状态、持久化格子坐标。
- 城市记录：名字、坐标、颜色、地标；半径与档位自动计算。
- 构建时运行排布脚本，输出每座城的半径和每个社群的格子，前端只负责渲染。
- 上传需要后端（GitHub Pages 只能放静态文件）：可选 GitHub Issue 表单加人工审核，或接数据库服务，待范围规则完成后再定。
